### Decentralized Data Ecosystems and Interface Heterogeneity
{:#related-work-ecosystems}

Decentralized data ecosystems consist of self-governed data stores, each individually positioned in the CAP space
and exposed through heterogeneous interfaces [](cite:cites phd-symposium).
Unlike distributed databases under centralized management, they have no unifying mission.

Our goal is to develop a CRDT for RDF that can work across the heterogeneous ecosystem depending only on
unifying aspects of the ecosystem.
To this end, our solution to offline first is the use of a state based CRDT using native RDF,
meaning all required information is included in the state of the data itself, and the data is RDF.
With this choice, the self-governed datastore does not need any special functionality to support the CRDT.
Only requiring that our communication channel eventually sends the updated state to every replication.

### CRDTs

The [m-ld project](cite:cites m-ld) provides a JavaScript CRDT engine for RDF with a similar eventual-consistency goal but requires a dedicated m-ld domain server,
making it less compatible with the heterogeneous nature of descentralized data ecosystems.
[Braid-HTTP](cite:cites braid) proposes adding merge-type headers to HTTP, which is complementary to our approach and could replace our custom patch encoding in a future version.
[Gruss et al.](cite:cites solid-crdt-yjs) suggest storing:
1. the latest state of an RDF document allowing non-CRDT aware clients to consume the data, and
2. a binary state representation of the documents CRDT as produced by a user chosen CRDT library (e.g. [Yjs](https://yjs.dev/) or [automerge](https://automerge.org/))  
3. a hypermedia-description of the CRDT and it's supported operations.

Within our use case, we want to enable non-CRDT aware clients to read the data, while storing all required information in a single doucment.
Since we want to abstract on the RDF-dataset level, at which only set based operations exist, we limit ourselves to set CRDTs. 
To this end, the [SU-Set](cite:cites rdf-crdt) introduce an extension to the generic [Observe Remove (OR-) Set](cite:cites CRDTs) for RDF.
In their work, they map all SPARQL Update 1.1 insert/delete operations to OR-Set operations,
thereby optimizing the CRDT such that a single operation send over the network handles the addition and removal of multiple triples,
where the basic OR-Set operations would handle the addition and deletion of only a single element in the set.

To support the use-case of decentralized data ecosystems, often relieing on the HTTP state-transfer protocol,
we choose a flow where the whole state is writen to a personal datastore, and all interactions flow through that store,
following the classical client-server architecture.
