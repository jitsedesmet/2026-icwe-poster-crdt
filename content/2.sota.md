### Decentralized Data Ecosystems and Interface Heterogeneity
{:#related-work-ecosystems}


Decentralized data ecosystems consist of self-governed data stores, 
each individually positioned in the CAP space and exposed through heterogeneous interfaces [](cite:cites phd-symposium).
Unlike distributed databases under centralized management, 
they share no unifying infrastructure.
Our goal is a CRDT for RDF that works across such ecosystems by depending only on what every participant already has:
the ability to store and exchange RDF data.
By choosing a state-based CRDT encoded entirely in native RDF,
all bookkeeping is contained within the data itself — no special server functionality is required.

### CRDTs

The [m-ld project](cite:cites m-ld) provides a JavaScript CRDT engine for RDF with a similar eventual-consistency goal,
but requires a dedicated m-ld domain server, making it a poor fit for heterogeneous decentralized ecosystems.
[Braid-HTTP](cite:cites braid) proposes adding merge-type headers to HTTP,
which is complementary to our approach and could replace our custom patch encoding in a future iteration.
[Gruss et al.](cite:cites solid-crdt-yjs) store the latest RDF state alongside a binary CRDT representation from a user-chosen library (e.g. Yjs or Automerge),
plus a hypermedia description of supported operations.
While this lets non-CRDT-aware clients consume the data, it relies on a separate binary blob outside the RDF dataset.
We instead aim to keep everything within a single RDF document, making the CRDT state itself queryable
and avoiding a consistency boundary problem where a standard HTTP server cannot atomically update multiple resources.

Since we abstract at the RDF dataset level — where only set-based operations exist — we limit ourselves to set CRDTs.
The [SU-Set](cite:cites rdf-crdt) extends the generic [Observe-Remove Set (OR-Set)](cite:cites CRDTs) for RDF,
mapping all SPARQL Update 1.1 insert/delete operations to OR-Set operations.
This allows a single network message to handle the addition and removal of multiple triples, whereas a basic OR-Set would handle only one element at a time.
In contrast to SU-Set, we target decentralized ecosystems that rely on HTTP's state-transfer model,
and therefore follow a classical client-server flow where the full state is written to a personal datastore and all interactions pass through it.
